## Issue 1（优先）

**标题**

```
aimer.cpp choose_aim_point 用 ekf_x()[8]（半径 r）判断小陀螺，导致非前哨站目标几乎永远不进入陀螺选板分支
```

**正文**

```markdown
您好，感谢开源 sp_vision_25，阅读代码时发现一处疑似状态下标误用，提出来供参考。

**版本**：main @ bd9f5e7（与 2025 发布版 zip 内容一致）

**位置**：`tasks/auto_aim/aimer.cpp` 第 163 行

```cpp
// 不考虑小陀螺
if (std::abs(target.ekf_x()[8]) <= 2 && target.name != ArmorName::outpost) {
```

**状态向量定义**（`tasks/auto_aim/target.cpp` 第 34 行）：

```cpp
// x vx y vy z vz a w r l h
```

即 `[6]=a 角度`，`[7]=w 角速度`，`[8]=r 半径`。

**问题**：第 163 行的意图（注释「不考虑小陀螺」）是按角速度判断，但取的是 `[8]`（半径 r）。
而 `Target` 自身会把 r 约束在合理范围内（`target.cpp` 第 243 行 `r_ok = ekf_.x[8] > 0.05 && ekf_.x[8] < 0.5`），所以 `|r| <= 2` 对正常目标恒成立。

**后果**：
- 除前哨站外，所有目标无论转多快都走「非陀螺」分支（±60° 可射范围 + 锁板逻辑）；
- 第 192–206 行的陀螺选板逻辑（按 `ekf_x[7]` 方向选「即将转来」的装甲板）以及配置项 `comming_angle` / `leaving_angle`，对步兵、英雄、哨兵等目标实际上不会生效。

同一文件第 204–205 行、`target.cpp` 第 132 行都使用 `[7]` 作为角速度，说明 `[8]` 应为笔误。

**建议改法**（一行）：

```cpp
if (std::abs(target.ekf_x()[7]) <= 2 && target.name != ArmorName::outpost) {
```

**验证方法**：
1. 在第 163 行前加日志打印 `ekf_x()[7]` 与 `ekf_x()[8]`，用小陀螺录像（或 `tests/` 下的离线回放）跑一次：`[8]` 始终在 0.2 左右，`[7]` 才随转速变化；
2. 修改后对高速小陀螺目标，可以观察到选板进入 coming/leaving 分支（在 192 行后加日志即可确认），选板行为与注释意图一致。

如果是有意为之（例如实测后决定关闭陀螺分支），也麻烦说明一下，那样更建议直接删掉该分支或改注释，避免后来者误读。谢谢！
```

## Issue 2（优先）

**标题**

```
aimer.cpp 高/低速延时判断 ekf_x()[7] > decision_speed_ 未取绝对值，反向旋转始终走低速延时（与 planner.cpp 不一致）
```

**正文**

```markdown
您好，这是另一处与转速相关的小问题。

**版本**：main @ bd9f5e7

**位置**：`tasks/auto_aim/aimer.cpp` 第 40–41 行

```cpp
double delay_time =
  target.ekf_x()[7] > decision_speed_ ? high_speed_delay_time_ : low_speed_delay_time_;
```

`[7]` 为角速度 w（`target.cpp` 第 34 行 `x vx y vy z vz a w r l h`），带符号，正负代表旋转方向（同文件第 204–205 行也按 `ekf_x[7] > 0 / < 0` 区分方向）。

**问题**：这里直接拿带符号的 w 与 `decision_speed_`（各 yaml 中为 7~12 rad/s 的正数）比较。目标反向（w < 0）高速旋转时，条件恒为假，始终使用 `low_speed_delay_time_`。

**仓库内不一致**：`tasks/auto_aim/planner/planner.cpp` 第 100–101 行的同一逻辑已正确取绝对值：

```cpp
std::abs(target->ekf_x()[7]) > decision_speed_ ? high_speed_delay_time_ : low_speed_delay_time_;
```

**后果**：同样转速的小陀螺，顺时针和逆时针时预测提前量不同；反向高速旋转时延时补偿偏小，命中率表现出方向不对称。

**建议改法**（一行）：

```cpp
std::abs(target.ekf_x()[7]) > decision_speed_ ? high_speed_delay_time_ : low_speed_delay_time_;
```

**验证方法**：
1. 打印 `ekf_x()[7]` 与选中的 `delay_time`，分别用正转、反转的小陀螺录像回放：修改前反转时 `delay_time` 恒为低速值；
2. 修改后两个方向在 |w| 超过阈值时都切到 `high_speed_delay_time_`，与 planner 行为一致。

谢谢！
```

## Issue 3（可选，中置信）

**标题**

```
shooter.cpp 开火判定中的 yaw 差未做角度回绕（limit_rad），目标在 ±180° 附近时可能误判为指令突变而不开火
```

**正文**

```markdown
您好，还有一处不太确定、想请教的问题。

**版本**：main @ bd9f5e7

**位置**：`tasks/auto_aim/shooter.cpp` 第 31–34 行

```cpp
if (
  std::abs(last_command_.yaw - command.yaw) < tolerance * 2 &&
  std::abs(gimbal_pos[0] - last_command_.yaw) < tolerance &&
  aimer.debug_aim_point.valid) {
```

**问题**：`command.yaw` 来自 `aimer.cpp` 第 120 行 `std::atan2(...) + yaw_offset_`，取值约在 (-π, π]；调用方传入的 `gimbal_pos[0]` / `ypr[0]` 来自 `tools::eulers(...)`，同样落在 (-π, π]。两者直接相减，没有经过 `tools::limit_rad`。

当目标在世界系 yaw 约 ±180° 附近来回跨越时，两帧指令差会从约 0 跳到约 2π，被判定为「command 突变」而不开火；云台角与指令分处 ±π 两侧时，第二个条件同理不成立。

**影响范围**：`src/sentry*.cpp`、`src/uav*.cpp`、`tasks/auto_aim/multithread/commandgener.cpp` 中使用 `Shooter::shoot` 的入口。只有世界系 yaw 零点设置得让目标落在 ±180° 附近时才会触发，所以平时不容易发现。

**建议改法**：

```cpp
std::abs(tools::limit_rad(last_command_.yaw - command.yaw)) < tolerance * 2 &&
std::abs(tools::limit_rad(gimbal_pos[0] - last_command_.yaw)) < tolerance &&
```

（`tools/math_tools.hpp` 已经包含，无需新增依赖。）

**验证方法**：构造 `last_command_.yaw = 3.13`、`command.yaw = -3.13`、`gimbal_pos[0] = 3.13` 的单元输入。修改前 `shoot()` 返回 false，修改后在 tolerance 内返回 true。

如果下位机或上层已经保证 yaw 不会跨越 ±π（例如使用连续角），请忽略此条，也欢迎指正。谢谢！
```
